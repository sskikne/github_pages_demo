What is GitHub Pages?

GitHub Pages is a free service that turns your code into a live website. You upload your files to GitHub, flip a switch, and your site is available at a public URL that you can share with anyone.

It works by serving static files — HTML, CSS, JavaScript, images, and data files. There are no servers to manage, no hosting fees, and no infrastructure to set up.

What Won't Work on GitHub Pages

GitHub Pages only serves files. It cannot run code on a server. If your app depends on any of the following, GitHub Pages is not the right fit:

  • Server-side search If your app sends search queries to a backend endpoint (including the Learning Commons Knowledge Graph search endpoint), those queries will not work. You can still display pre-loaded data, but live search requires a server.
  • Databases PostgreSQL, MongoDB, SQLite, or any other database. All data must be saved as static files that ship with your site.
  • User login and accounts Sign-up, sign-in, and session management all require a server. Third-party auth services (like "Sign in with Google") that are entirely client-side may still work.
  • API routes Next.js API routes (/api/*), Express servers, or any backend endpoint you've built. These run on a server and are not supported.
  • Real-time features WebSockets, live chat, collaborative editing, or anything that maintains a persistent connection to a server.
  • Server-side rendering getServerSideProps in Next.js or any code that runs on the server for each page request. Static generation (getStaticProps) is fine because it runs once at build time.

If your app needs any of the above, consider Vercel, Netlify, or Railway instead. These platforms can run server-side code.

Setting Up Your GitHub Account

Create a GitHub account

If you don't already have a GitHub account, go to github.com/signup and follow the steps. You'll need an email address. The free plan is all you need.

Install the GitHub CLI

The GitHub CLI (gh) lets you interact with GitHub from your terminal — the same terminal where you use Claude Code. Install it for your operating system:

Mac (using Homebrew):

brew install gh

Windows (using winget):

winget install --id GitHub.cli

Linux (Debian/Ubuntu):

(type -p wget >/dev/null || (sudo apt update && sudo apt-get install wget -y)) \
  && sudo mkdir -p -m 755 /etc/apt/keyrings \
  && out=$(mktemp) && wget -nv -O$out https://cli.github.com/packages/githubcli-archive-keyring.gpg \
  && cat $out | sudo tee /etc/apt/keyrings/githubcli-archive-keyring.gpg > /dev/null \
  && sudo chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg \
  && echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" | sudo tee /etc/apt/sources.list.d/github-cli-stable.list > /dev/null \
  && sudo apt update \
  && sudo apt install gh -y

You can also find full installation instructions at cli.github.com.

Sign in to the GitHub CLI

After installing, open your terminal and run:

gh auth login --scopes workflow

The --scopes workflow flag is important. Without it, you won't be able to push the deployment workflow file that makes GitHub Pages work. If you skip this flag, you'll get an error later that says "refusing to allow an OAuth App to create or update workflow."

This will walk you through a short sign-in process:

  1. Select GitHub.com when asked which account to log into.
  2. Select HTTPS as the preferred protocol.
  3. Select Login with a web browser when asked how to authenticate.
  4. Copy the one-time code shown in your terminal.
  5. Press Enter — your browser will open to a GitHub page where you paste the code.
  6. Authorize the CLI and return to your terminal. You should see a confirmation message.

To verify it worked, run:

gh auth status

You should see your GitHub username and a confirmation that you're logged in.

Already logged in?

If you've already signed into the GitHub CLI but didn't include the workflow scope, you can add it without signing out:

gh auth refresh --scopes workflow

Make Your App Deployable

If you built your app with Claude Code, it's likely a Next.js or React (Vite) project. These frameworks can produce static files that GitHub Pages can serve, but they need some configuration first.

Instead of making these changes yourself, paste the following prompt into Claude Code. It will detect your project type and make all the necessary changes automatically.

Before running this prompt, replace <repo-name> with the name you plan to give your GitHub repository (for example, my-knowledge-app). This is needed so that asset paths work correctly on GitHub Pages.

Copy and paste this into Claude Code
I want to deploy this project to GitHub Pages. Make it fully static and deployable. My repository name will be <repo-name>. 1. Detect whether this is a Next.js or Vite/React project, then follow the appropriate steps below. 2. If this is a Next.js project: - Set output: 'export' in next.config.js (or next.config.mjs/ts) - Remove any API routes (pages/api/ or app/api/ directories) - Replace any getServerSideProps with static data or getStaticProps - Set basePath and assetPrefix to '/<repo-name>' in the Next.js config - Remove the 'images' config or set it to use unoptimized: true (the Next.js image optimizer requires a server) - Create a .nojekyll file in the public/ directory 3. If this is a Vite/React project: - Set base: '/<repo-name>/' in vite.config.js (or .ts) 4. For any data fetched from the Learning Commons Knowledge Graph API: - Fetch data from https://api.learningcommons.org/knowledge-graph/v0 (API docs: https://docs.learningcommons.org/knowledge-graph/getting-started/quickstart) - Save the API response as a static JSON file in the public/data/ directory - Update all API calls in the app to import or fetch from the local JSON file instead - Remove any search functionality that depends on a server-side search endpoint - Leave a comment noting where the cached data came from and when it was last updated 5. Remove any backend dependencies from package.json (express, database clients, server-only packages) and any server files. 6. Create a GitHub Actions workflow at .github/workflows/deploy.yml that: - Triggers on push to the main branch - Installs dependencies and builds the project - Deploys the build output directory to GitHub Pages using the actions/deploy-pages action - Uses actions/configure-pages, actions/upload-pages-artifact, and actions/deploy-pages 7. Build the project locally to confirm it succeeds, and report any errors you find.

After Claude Code finishes, review the changes it made. The key things to confirm:

  • The project builds without errors (npm run build)
  • The build output is a folder of static files (usually out/ for Next.js or dist/ for Vite)
  • There are no remaining references to server-side features
  • A .github/workflows/deploy.yml file has been created

Deploy to GitHub Pages

Now that your app builds to static files, you can deploy it. You can do this from your terminal, or paste these instructions into Claude Code and let it handle it for you.

  1. Create a GitHub repository

    Run this command in your project directory to create a new public repository on GitHub:

    gh repo create <repo-name> --public --source=. --remote=origin --push

    This creates the repository, connects your local project to it, and pushes your code in one step. The push will also trigger your deployment workflow, but it may fail because GitHub Pages isn't enabled yet — that's normal.

  2. Enable GitHub Pages

    Tell GitHub to serve your site using GitHub Actions (which is where your deploy workflow runs):

    gh api repos/<your-github-username>/<repo-name>/pages \
  --method POST \
  --field build_type=workflow

    If you're not sure what your GitHub username is, run gh api user --jq .login to find it.

  3. Trigger a deployment

    If the first workflow run failed (because Pages wasn't enabled yet), re-run it now:

    gh run rerun $(gh run list --workflow=deploy.yml --limit=1 --json databaseId --jq '.[0].databaseId')

    Or, if you prefer, just push a small change to trigger a new run:

    git commit --allow-empty -m "Trigger deploy"
git push

    Check the status of the run:

    gh run list --workflow=deploy.yml

    Wait for it to show completed and success. This usually takes about 30 seconds to a minute.

  4. Find your site URL

    Your site is published at:

    https://<your-github-username>.github.io/<repo-name>/

    You can also find the URL by running:

    gh api repos/<your-github-username>/<repo-name>/pages --jq .html_url

    Open that URL in your browser. Your app is live and shareable.

Updating your site

Every time you push changes to the main branch, GitHub Actions will automatically rebuild and redeploy your site. To push changes:

git add -A
git commit -m "Update site"
git push

Troubleshooting

Blank page after deployment

This is almost always a path issue. GitHub Pages serves your site at /<repo-name>/, not at the root /. Make sure:

  • Next.js: basePath and assetPrefix are set to '/<repo-name>' in your Next.js config
  • Vite: base is set to '/<repo-name>/' in vite.config.js

404 errors when refreshing a page

GitHub Pages doesn't support client-side routing out of the box. If your app uses React Router or Next.js dynamic routes, refreshing a page that isn't index.html will return a 404.

The fix: add a 404.html file to your build output that's a copy of index.html. GitHub Pages serves 404.html for any path it doesn't recognize, which lets your client-side router take over. Ask Claude Code to set this up for you.

Images or assets not loading

Check that your asset references use relative paths or include the basePath. An image at /images/logo.png will fail — it should be /<repo-name>/images/logo.png or use a relative path.

"Refusing to allow an OAuth App to create or update workflow"

This error means your GitHub CLI token doesn't have the workflow scope. Fix it by running:

gh auth refresh --scopes workflow

Then try your push again.

Build fails in GitHub Actions

Check the build logs:

gh run view --log-failed

Common causes:

  • Missing dependencies — make sure package-lock.json is committed
  • Node version mismatch — the workflow should specify the same Node version you use locally
  • Server-side code that wasn't fully removed (e.g., a lingering getServerSideProps)

The GitHub Pages setting says "disabled"

If the gh api command to enable Pages returned an error, you can enable it manually:

  1. Go to your repository on github.com
  2. Click Settings (the tab along the top)
  3. In the left sidebar, click Pages
  4. Under Build and deployment, set the source to GitHub Actions

Changes aren't showing up

After pushing, it takes 1–2 minutes for the GitHub Actions workflow to build and deploy. Check the status with gh run list --workflow=deploy.yml. If the latest run succeeded but you still see old content, try a hard refresh in your browser (Ctrl+Shift+R or Cmd+Shift+R).
